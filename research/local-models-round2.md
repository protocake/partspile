# Local models, round 2: Qwen3.6-35B instruction-following investigation

Date: 2026-09-07. Scope: web research (r/LocalLLaMA is poorly indexed right now; most evidence below is GitHub issues, HF model cards/discussions, vendor docs, and 2026 benchmark/guide sites). Judged against our observed failure profile: vision/OCR decent, schema compliance fine, but (a) assemblies decomposed into 5-9 sub-parts despite explicit rules, (b) `needs_reshoot=true` never set (0/8), (c) ~90s/photo.

## 1. Verdict: KEEP Qwen3.6-35B-A3B — the failure profile matches harness bugs, not model capability. Fix three things, re-run one eval iteration, then decide.

The observed signature — *vision fine, schema fine, prompt rules ignored* — is exactly what two documented Ollama behaviors produce:

**Smoking gun A: silent context truncation drops the HEAD of the prompt.**
Ollama defaults to a 4096-token context and silently truncates longer prompts, keeping the *tail* — the system prompt and rules at the start are the first thing discarded, with a normal 200 response and no warning. The OpenAI-compat `/v1/chat/completions` endpoint cannot raise `num_ctx` per request at all (open since 2024, still not landed). A Qwen-VL-family image costs on the order of 1-2.5K tokens at typical resolutions; image + our long rules prompt + thinking output almost certainly blew past 4096. Schema stayed valid because Ollama's `format` grammar is enforced at decode time regardless of what the model saw. This single bug reproduces our exact failure profile.

**Smoking gun B: thinking mode was on the whole time.**
Qwen3.6 is thinking-by-default (`<think>…</think>` before every answer; toggled off only via `think: false` on Ollama's native API or `chat_template_kwargs: {"enable_thinking": false}` elsewhere). That explains the 90s/photo (5-6x slowdowns vs non-thinking are reported for sibling models). Research (ReasonIF, 2025/26) shows reasoning models measurably *fail instruction-following during reasoning*; and Ollama has a history of thinking+`format` interaction bugs (invalid JSON in #10929; and #15260/#14645: `think=false` + `format` **silently dropped the format constraint entirely** for the qwen3.5 series and gemma4 — closed via PRs #15678/#15392, so upgrade Ollama before trusting the combo).

Qwen family template handling in Ollama is also historically flaky — qwen3.6 tool-template drift (#16383), qwen3-vl shipped with *no system prompt support at all* (#13471) and no thinking toggle in its template (#14798), qwen3.5 renderer/parser mismatch (#14493). Before blaming the model, run `ollama show --template qwen3.6:35b` and confirm `{{ .System }}` is actually rendered.

**Why not switch immediately:** Qwen3.6-35B-A3B's own card and MM-IFEval-Pro data don't show an unusually weak instruction-follower (Qwen3.5-35B-A3B was one of the *stable* models under instruction-hijacking in MM-IFEval-Pro, Sept 2026), and no current community source reports the decomposition/flag failures we saw as a known model trait. The cheap experiment (below) isolates model vs harness.

**If it still fails after the fixes, switch to (in order):**
1. `gemma4:26b` (Ollama official; 26B-A4B-it MoE, 19GB, ~3.8B active — fast on M4 Max). Multimodal from the ground up, **native system role**, thinking **off by default** (enabled only by `<|think|>` in the system prompt), day-one Ollama/MLX support, Gemma line's traditional strength is exactly instruction adherence. Note its convention: **images before text**. OCR is competitive but Qwen still leads document/OCR benchmarks, so spot-check chip-marking reads.
2. `qwen3-vl:32b` (dense Instruct, non-thinking, 21GB Q4). The Qwen3-VL-Instruct line has the best measured baseline instruction-following among open VLMs in MM-IFEval-Pro (its 8B scored 78.7% vs InternVL3.5-8B's 64.6%). Caveats: ~10 months old, and the Ollama build's template historically lacked system-prompt support — verify or put everything in the user turn.
3. `GLM-4.6V-Flash` (9B, LM Studio official / `gurubot/GLM-4.6V-Flash-GGUF:Q4_K_M` on Ollama) — strong small VLM with native visual tool use; least community evidence on strict negative-constraint adherence.
Not recommended: MiniCPM-V 4.6 (1.3B, too small for our task), Llama 4 vision (no 2026 evidence of IF advantage), InternVL3.5 (worst measured baseline IF of the group).

## 2. Top 3 prompt techniques for instruction adherence (Qwen3.6, this task)

1. **Convert both failing rules from prohibitions into schema-forced positive decisions.** Negative constraints ("do NOT list sub-components") reliably underperform positive ones — LLMs act on the named thing ("pink elephant" effect), and compliance collapses when a constraint fights the model's prior (an ESP32 devkit *is* made of parts). Concretely: (a) state the granularity rule positively — "One entry per item a hobbyist would buy or sell as a unit. An assembled board/module/devkit is ONE part." — and add a required early JSON field like `"unit_type": "discrete_component" | "module_or_assembly" | "bare_board"` so the assembly-vs-component decision is an explicit output, not a suppressed behavior; (b) replace the never-set boolean with a forced choice the model must reason into: put `"legibility": "fully_readable" | "partially_readable" | "unreadable"` and `"reshoot_reason": string|null` *before* `needs_reshoot` in the field order (models fill fields in order; an upstream forced classification makes the downstream boolean nearly free). Derive `needs_reshoot` in code from `legibility` if we can (schema change → ask Ben) or keep it and let the ordering carry it.
2. **One-shot faked-dialogue example covering both rules.** Practitioners get Qwen-VL formats to stick by inserting a fabricated prior exchange: a user turn (image + same instructions) and a hand-written ideal assistant JSON answer. Include one example where a devkit photo yields a SINGLE entry, and one where a blurry part yields `needs_reshoot: true`. This conditions far harder than more rule text. (Text example without a real image also works and costs no image tokens.)
3. **Placement + repetition + sampling.** Keep the system prompt short; put the task rules in the user message *after* the image (Qwen's own cookbooks use image-then-text; the tail of the prompt also survives any truncation), and restate the two critical rules as the final two lines. Use Qwen3.6's non-thinking recommended sampling — temperature 0.7, top_p 0.8, presence_penalty 1.5 — or drop toward temp 0.2-0.6 for extraction, but do **not** use pure greedy/temp 0: Qwen explicitly warns greedy decoding causes degradation and repetition loops on this family. Finally, keep a validator+retry loop: on a rule violation (e.g., >3 entries from one photo), re-prompt quoting the specific violation — the only technique that works across all models.

## 3. Ollama config gotchas for qwen3.6 (do these before the re-run)

- **Context:** create a derived model — `FROM qwen3.6:35b` + `PARAMETER num_ctx 16384` — or set `OLLAMA_CONTEXT_LENGTH`. The OpenAI-compat endpoint ignores `num_ctx` and env-var overrides in some versions; prefer the native `/api/chat` from our provider code, which also accepts `options.num_ctx` per request. Symptom of getting this wrong is exactly what we saw: silent head-of-prompt truncation.
- **Thinking:** disable per request with `think: false` (native API / Python `think=False`). It cannot be set in a Modelfile (`PARAMETER think false` is an open feature request, #14809); the community template hack (`<think></think>` injected after system) works but breaks across Ollama upgrades. Expect a large speed win vs our 90s/photo.
- **`think:false` + `format` regression:** on affected Ollama versions the format grammar was *silently dropped* for qwen3.5-family/gemma4 templates (#15260). Upgrade to current Ollama and assert `json.loads` + schema-validate every response in eval; if format breaks with `think:false`, omit `think` and instead pass `chat_template_kwargs`/`/no_think` — or accept default thinking and raise num_ctx enough to hold the thinking tokens.
- **Template sanity:** `ollama show --template qwen3.6:35b` — confirm `{{ .System }}` and think-toggle logic exist (qwen3-vl shipped without both; qwen3.6 has documented tool-template drift, #16383). If the system block is missing, move everything into the user message.
- **OpenAI-compat endpoint:** `temperature`/`top_p`/`presence_penalty` pass through fine, but `num_ctx`, `think`, and `chat_template_kwargs` do not — another reason to use the native API in `partspile/providers/`.
- **MLX route:** `qwen3.6:35b-mlx` (24GB) exists in the Ollama library; LM Studio's `qwen/qwen3.6-35b-a3b` supports `chat_template_kwargs: {"enable_thinking": false}` properly if we ever want the officially supported thinking toggle.
- Ollama cannot load the unsloth Qwen3.6 GGUFs with a separate `mmproj` file — stick to the official `qwen3.6:*` library tags for vision.
